00What the tool actually is

bp is a scaffold-and-verify CLI for agentic governance files. It detects a repo's topology, renders Handlebars scaffolds for rules / skills / agents, validates them, and translates them across 31 AI coding backends through a backend-neutral BlueprintIR.

DETECTORfingerprint the repo
TEMPLATERrender *.hbs scaffolds
VALIDATOR4-layer checks
TRANSLATORIR ↔ 31 backends
Genuine value today: the backend-neutral IR + 31 adapters (real cross-tool interop), marker-based brownfield-safe merging, and origin-blind validation. For a team standardizing agentic config across Claude Code / Cursor / Windsurf / Gemini, that is a legitimate problem solved.

Q1How does it compare the skills and rules domains?

Your question: Does it compare the raw text of these rules, or use another pattern?

Structured field comparison on parsed frontmatter — NOT raw-text/file diffing, and NOT any semantic / AST / embedding technique.

Step 1 — Parse, don't read

Files are loaded with gray-matter, splitting YAML frontmatter from the body. The key asymmetry between the two domains:

DomainWhat "is" the objectFields extracted
Rulefrontmatter only — markdown body is discardedid, scope, severity, action, rationale, tags
Skillfrontmatter + prose bodyname, description, when_to_use, tools_required, procedure

So a rule is its frontmatter; a skill is its frontmatter plus its body (procedure: parsed.content.trim()).

Step 2 — Compare field-by-field with exact equality

src/ecosystem/diff.ts:108–136

// rules
if (left.action !== right.action) changes.push("action modified");
// skills
if (left.procedure !== right.procedure) changes.push("procedure modified");

Both use exact string equality (!==). Arrays (tags, tools_required) use set add/remove diffing. There is no fuzzy match, Levenshtein, token similarity, or embedding anywhere in the codebase.

The only computeSimilarity (src/validator/drift.ts:306) is binary: 
return hash1 === hash2 ? 1.0 : 0.0;
…over a lightly normalized (lowercase + whitespace-collapsed) SHA-256. It is an identity check, not a graded similarity score.

Step 3 — Domain-specific structural checks (beyond the diff)

DomainExtra checkTechnique
RulesContradiction detectionHardcoded ANTONYM_PAIRS table (~10 pairs); lowercases action and runs .includes("must use") vs .includes("never use"). String pattern matching, not meaning.
SkillsCircular-dependency detectionBuilds a graph from uses/requires_skills frontmatter, runs Tarjan's SCC. The one genuinely non-textual comparison.
Cross-domainRule → skill referencesRegex [[skill:x]] / @skill:x extracted from action, validated by set membership against skill names.
⚠️ Naming oversells it. "Semantic drift" (src/observability/semantic-drift.ts) is actually behavioral-metric drift — success rates & invocation counts, not text meaning. And computeSimilarity is boolean identity, not similarity.

Q2Does it handle dynamic user-created skills & rules, or only its own scaffolds?

Your question: Does the package handle user dynamic creation/modification, or just the scaffold files it creates?

Mixed — and this split is the crux of your governance concern. Behaviour differs by command.

CapabilityUser-authored files?Where / why
Validate (verify, drift)YESGlobs manifest.file_patterns.{rules,skills,agents} — origin-blind (src/validator/index.ts:91–109)
Translate / convertYESAdapters parse whatever exists on disk into the IR
Merge on re-scaffoldONLY WITH MARKERSBlock-merge needs <!-- bp-generated:begin/end --> or <!-- bp:preserve --> (src/templater/merger.ts)
Scaffold / generateNOTemplater only walks bundled *.hbs (src/templater/index.ts:164) — no renderRule()/renderSkill() from user input
Track origin (managed vs user)NONo manifest/lockfile of what bp created
In plain terms: verify and convert fully respect dynamic user content — a hand-written .claude/skills/my-thing.md is parsed, validated, and translated like any scaffold. But generation is one-directional and template-bound, and there is no record of which files bp owns.
  • On re-run, a user file with no markers is skipped by default (safe) or clobbered with --force (src/templater/writer.ts).
  • A user editing inside a generated block loses that edit on the next render unless wrapped in bp:preserve.

01Does the flow offer real value — and what's missing?

✅ Value it has now

  • Backend-neutral IR + 31 adapters → real cross-tool interop.
  • Marker-based merge → brownfield-safe regeneration.
  • Origin-blind validation → user content is checked, not just scaffolds.

🔧 What's missing for durable, change-adopting governance

Ordered by leverage. Gap #1 is the root cause that the others flow from.

  • No ownership manifest. Without a lockfile of hashes/paths bp generated, the tool can't tell its drift from an intentional developer change. This is the single biggest blocker to "governance that adopts developer changes."
  • No auto-marker adoption. Preservation requires the user to know about bp:preserve; existing user files stay fragile.
  • Comparison too literal to govern meaning. Any whitespace/wording change reads as "modified," while genuinely contradictory rules pass unless they hit the ~10 hardcoded antonyms.
  • Generation can't round-trip. The IR can read user skills/rules but the templater can't write arbitrary (non-template) entries back — no "edit once, regenerate everywhere" loop.
  • Misleading "semantic"/drift naming. Both engines are metric/identity based; either rename honestly or implement graded content similarity.

02Recommendations

1

Ownership manifest HIGH

Add .bp/manifest.json mapping path → content-hash → source-template. Lets verify distinguish "you changed this on purpose" from "this rotted." Root fix — unlocks #2–#4.

2

A bp adopt command HIGH

Wrap existing user rules/skills in managed markers automatically, making their content first-class instead of fragile — no need for users to learn bp:preserve.

3

Smarter comparison MED

Normalize before diffing (whitespace/case) so cosmetic edits don't read as changes; generalize contradiction detection beyond the hardcoded antonym list toward structured-intent comparison.

4

IR → file round-trip MED

Let the templater emit arbitrary IR entries (not just bundled *.hbs), enabling "edit in one backend, regenerate everywhere." Turns a one-shot scaffolder into a governance hub.

5

Honest naming or real similarity MED

Rename "semantic drift" → "behavioral drift" and the boolean check → "identity check," or implement graded similarity so "diverged significantly" is meaningful.

Suggested first slice: Recommendations #1 + #2 on branch claude/blueprint-repo-analysis-hEiyJ. Together they convert bp from a scaffolder into governance that survives developer edits.
